# Правила для агентов — workshop_vibe

Четыре AI-агента параллельно и автономно делают магазин «Ступка и колба» для воркшопа ИТМО. Цель — лучший результат среди команд: безупречный минимум, все F1–F10, B1–B6, Q1, Q2, D1, D2, сильный дизайн, тесты, README и демо.

Читай в таком порядке:
1. Этот файл — как работаем.
2. `docs/CONTRACT.md` — что строим: структура, владельцы файлов, данные, API, `data-testid`, критерии готовности.
3. `.team/prompts/<твоя-роль>.md` — твой бэклог.

## Режим скорости — главное правило
- Цель — работающий и визуально впечатляющий магазин примерно за 2 часа. «Хорошо и вовремя» лучше, чем «идеально и поздно».
- Порядок: минимум ТЗ → F1–F10 → B1–B6 → ключевые тесты → README и сдача. Всё остальное — только после этого.
- Таймбокс: пункт занимает больше 15 минут или не чинится с двух попыток — упрости решение или пропусти, запиши в свой статус и иди дальше.
- Тесты — только ключевые сценарии. Не пиши исчерпывающих наборов, не гоняй тяжёлые проверки на каждый push.
- Не делать: Lighthouse и метрики, оптимизацию производительности, абстракции «на будущее», рефакторинг ради рефакторинга, Windows-специфику, вылизывание редких граничных случаев.
- Исключение — внешний вид. На визуал время тратить можно и нужно: это то, что видят менторы.

## Текущее состояние (обновляй при крупных изменениях)
- Фронтенд готов и проверен в браузере: минимум ТЗ, F1–F10, тёмная тема, мобильная панель корзины, печать промокода, офлайн-режим и подготовка к API (`site/js/api.js`). Файлы `site/**` и `tests/unit/shop.test.js` не переписывать с нуля — только дорабатывать и чинить.
- Ещё не сделано: Go-backend B1–B6 (`backend`), e2e и CI (`qa`), DEMO.md и SUBMISSION.md (`lead`).

## Автономность
- Людей нет. Не задавай вопросов и не жди подтверждений. Неясно — прими лучшее решение в рамках контракта, запиши его в свой `.team/status/<роль>.md` и продолжай.
- Работай по приоритетам бэклога и не останавливайся до `.team/FREEZE`: закончил пункт — бери следующий. Всё готово — `git pull` → свой inbox → видимые пользователю баги.
- Перед каждой задачей `git pull`. Если в `main` есть `.team/FREEZE` — новых фич не начинать, только доводка, исправления, проверки и финальный push.
- Ждёшь чужой push (например, `store.js`) — не простаивай: делай следующую независимую задачу и периодически подтягивай `main`.

## Качество
- **Никаких комментариев в коде**: ни `//`, ни `/* */`, ни `<!-- -->`, ни `#` в YAML/Python, ни TODO/FIXME. Понятность — через имена и структуру. Допустимы только технические директивы: `"use strict"`, `//go:embed`, `//go:build`, shebang.
- Никакого мёртвого кода, `console.log`, отладочного вывода, закомментированных блоков, неиспользуемых файлов.
- Код чистый и читаемый, без оверинжиниринга: простые функции, понятные имена, без дублирования. Ошибки, которые может увидеть пользователь, обрабатываются; экзотику не трогаем.
- Frontend: HTML/CSS/JS без сборки и зависимостей. Работает с `http://`, на GitHub Pages в подпапке и через `file://` (двойной клик по `index.html` из ZIP). Только относительные пути `./…`. Никаких CDN и внешних запросов.
- JS: `"use strict"`, единственный глобал `window.Shop`, данные в DOM только через `textContent`/`createElement`/`<template>` (никакого `innerHTML` с данными), делегирование событий.
- CSS: токены в `:root`, mobile-first, `prefers-color-scheme`, `prefers-reduced-motion`, `:focus-visible`, цели касания ≥44px, контраст WCAG AA, без `!important`.
- Go: `gofmt`, стандартная библиотека + `modernc.org/sqlite` (без cgo), ошибки оборачиваются через `%w`, таймауты сервера и лимит тела запроса, без `panic` в рабочем коде.
- Тексты интерфейса — грамотный русский, единый тон. Цены — «1 290 ₽».
- Безопасность: секреты только в переменных окружения; `.env.example` с пустыми значениями; в `site/` нет ничего секретного; админ-токен никогда не попадает в JS.

## Git: trunk-based, прямо в `main`
1. Перед задачей: `git pull --rebase --autostash origin main`.
2. Маленькие атомарные коммиты, Conventional Commits на английском: `feat(ui): …`, `fix(api): …`, `test(e2e): …`, `docs: …`, `ci: …`.
3. `git add` только своих путей. Никогда `git add -A` / `git add .`.
4. Перед push — быстрые проверки своей зоны (до минуты). `python3 tests/smoke.py` — только если менял Go-код или структуру `site/`. Красное не пушить.
5. `git push origin main`. Отклонён — `git pull --rebase`, снова проверки, снова push.
6. Запрещено: `--force`, переписывание опубликованной истории, `git reset --hard` поверх чужой работы, коммит `shop.zip`, `*.db`, `node_modules`, `.env`.
7. Конфликт при rebase в чужом файле — бери версию из `origin/main`. В своём — объединяй обе стороны по смыслу и перепроверяй.
8. Push не реже раза в 10–15 минут: остальные должны видеть прогресс.

## Проверки

| Зона | Команда |
|---|---|
| unit JS | `node --test "tests/unit/*.test.js"` |
| Go | `go test ./...` |
| smoke | `python3 tests/smoke.py` |
| e2e | `cd e2e && npx playwright test` |

Красная проверка из-за чужого кода — задача в inbox владельца с шагами воспроизведения; сам не чини.

## Координация через репозиторий
- `.team/status/<роль>.md` — только твой файл: сделано (с ID задач), в работе, блокеры, решения, «баг, который нашли и исправили» (нужен для демо). Обновляй при каждом push.
- `.team/inbox/<роль>.md` — входящие задачи. Другие дописывают строку в конец файла: `- [ ] from <роль>: <что, где, шаги воспроизведения>`. Владелец меняет на `- [x]` и дописывает ` → <результат, коммит>`. Проверяй свой inbox при каждом pull. Конфликт в inbox — сохраняй обе строки.
- `.team/FREEZE` — сигнал финала.
- Контракт меняет только `lead`.
